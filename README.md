# دَفتَرچه

دفترچه‌ای برای اینکه بفهمی **الان چه کاری ارزش انجام دادن دارد** — یک اپ وب کامل، آفلاین‌پذیر و بدون حساب کاربری، برای کارهای روزانه، تمرکز، و خواندن.

داده‌ات روی دستگاه خودت می‌ماند؛ نه سروری برای حساب، نه همگام‌سازی ابری.

آدرس منتشرشده: <https://amirrezahajiabadi.github.io/daftarche/>

---

## قلمروهای اصلی

| بخش | چه می‌کند |
|---|---|
| **امروز** | صفحهٔ اول: سلام و تاریخ، افزودن سریع کار، پیشنهاد «الان چی کار کنیم؟» همراه با دلیل، کارهای امروز، پیشرفت امروز، حال‌وهوای روز. |
| **کارها** | اولویت، دسته‌بندی، مهلت، مدت تخمینی، یادآور، جستجو، فیلتر، مرتب‌سازی با درگ‌ودراپ، حذف با بازگردانی. |
| **تمرکز** | تایمر تمرکز با مدت قابل تنظیم، انتخاب کتاب برای جلسه، ثبت جلسه و امتیاز، ادامه دادن یک جلسهٔ نیمه‌کاره. |
| **سابقهٔ تمرکز** | جلسه‌های گذشته با عنوان کتاب، مدت، امتیاز و وضعیت تکمیل. |
| **بینش‌ها** | بازتاب آرام هفت‌روزه روی تمرکز و کارها، با آستانهٔ حداقل داده تا از نتیجه‌گیری زودهنگام پرهیز کند. |
| **کتابخانه** | قفسهٔ کتاب‌ها، هدف مطالعهٔ روزانه، درصد پیشرفت، صفحهٔ خوانده‌شده، قفسهٔ کتاب‌های تمام‌شده. |
| **خوانندهٔ PDF** | رندر با pdf.js، لایهٔ متن، انتخاب متن، هایلایت متن، هایلایت دست‌آزاد با سه ضخامت، پاک‌کن با بازگردانی، یادداشت، پیشرفت خواندن، و یک نوار ابزار پایین برای پیمایش صفحه، قلم، یادداشت‌ها و تنظیمات مطالعه. |
| **پروفایل و آمار** | نام و آواتار، روزهای پیاپی، نمودار هفتگی، مود روزانه، دستاوردها، تنظیمات تم و اعلان. |
| **اعلان‌ها** | یادآور محلی موعد کارها — سیستم اعلان رسمی نسخهٔ فعلی. Web Push زیرساخت اختیاری و موکول به آینده است (پایین را ببین). |

بخش‌های همراه: قورقوری (شخصیت راهنما)، تاسِ شانس برای انتخاب کار بعدی، صدای محیطی و موسیقی قابل بارگذاری.

## معماری

- **فرانت‌اند: JavaScript خالص و ماژولار.** بدون فریم‌ورک، بدون build step و بدون bundler. `index.html` یک `<script type="module">` را بار می‌گذارد و ماژول‌های `js/` با import استاندارد به هم وصل می‌شوند. CSS در حداکثر دسترس‌پذیری ساده و بدون پیش‌پردازش در پوشهٔ `css/` است.
- **حالت برنامه:** یک store سادهٔ مرکزی (`js/state.js`) با یک گذرگاه رویداد (`js/bus.js`)؛ رندر هر صفحه به‌صورت imperative و مستقل است.
- **تاریخ شمسی:** تبدیل‌های تاریخ در `js/jalali.js`، بدون وابستگی بیرونی.
## تم و رنگ

رنگ رابط از یک جدول پالت می‌آید و آن جدول یک تعریف بیشتر ندارد: `:root` در `css/base.css` رنگ‌های هر پالت («کاغذ»، «جنگل»، «شب») را به‌صورت `--pal-*` نگه می‌دارد و دو مصرف‌کننده دارد.

- **تم رابط:** `html[data-theme="…"]` هر پالت را روی توکن‌های معنایی (`--color-*`) می‌نویسد. «روشن» هم در جدول پالت‌هاست — همان توکن‌های `:root` است که کل طراحی با آن کشیده شده و پیش‌فرض هر کسی است که انتخاب نکرده.
- **قالب کارت آمار:** `[data-palette="…"]` همان پالت را به واژه‌های خود کارت (`--card-*`) و به نقطهٔ رنگی چیپ ترجمه می‌کند. پس یک پالت فقط یک‌جا نوشته می‌شود و کارت هرگز از اپی که از آن آمده جدا نمی‌افتد؛ «برنامه» هم یعنی «همان رنگی که همین حالا روی صفحه است».

- **چهار تم: روشن، کاغذ، شب، جنگل.** انتخاب در تنظیمات پروفایل یک ردیف چیپ است (همان کامپوننتی که قالب کارت آمار هم با آن ساخته می‌شود: `js/chipgroup.js`) و هر چیپ رنگ خودش را در نقطه‌اش نشان می‌دهد.
- **دکمهٔ تم در سرصفحه یک تپ است و فقط بین روشن و شب می‌چرخد.** انتخاب چهارراهه در تنظیمات است، جایی که هر گزینه نام دارد؛ برچسب دکمه هم می‌گوید همین تپ چه می‌کند.
- **`color-scheme` هر تم در همان بلوک نوشته می‌شود** تا مرورگر هم بداند کدام تم روشن است: نوار وضعیت، اسکرول‌بار و کنترل‌های خودش همرنگ تم می‌شوند، نه ترجیح سیستم.
- **`theme-color` از توکن `--color-bg` خوانده می‌شود** (`js/theme.js`)، همان توکنی که CSS با آن نقاشی می‌کند، پس نوار مرورگر و رنگ‌های اپ نمی‌توانند از هم جدا شوند.
- **بدون پرش، پیش از اولین نقاشی:** اسکریپت کوچک داخل `index.html` مقدار ذخیره‌شده را قبل از پارس شدن سند روی ریشه می‌نویسد و کلید قدیمی `dark` را به `night` ترجمه می‌کند. تم در `localStorage` با کلید `theme` می‌ماند و هر مقدار ناشناختهای بی‌صدا به پیش‌فرض برمی‌گردد.

## ناوبری و بازگشت

ناوبری درون‌برنامه‌ای یک «رد پا» است: هر جابه‌جایی یک قدم روی `history` مرورگر می‌شود و خودِ رد پا داخل همان entry (کلید `trail` در `history.state`) نگه داشته می‌شود. نتیجه این‌که دکمهٔ بازگشت روی صفحه، دکمهٔ برگشت مرورگر و ژست برگشت اندروید همه یک کار می‌کنند: یک قدم عقب روی همان رد پا. اگر مرورگر entry بی‌state بدهد، صفحه از هش آدرس خوانده می‌شود.

- **دکمهٔ بازگشت فقط روی صفحه‌هایی که تب‌بار ندارد.** چهار صفحهٔ اصلی (امروز، کارها، تمرکز، کتابخانه) با نوار پایین یک قدم فاصله دارند و برگشت اضافه در آن‌ها فقط شلوغی بود؛ پس کنترل «بازگشت» فقط در پروفایل و آمار تزریق می‌شود (در `app.js`، بالای سرصفحهٔ `main.app`) و آن هم وقتی که قدمی پشت سر باشد.
- **هش آدرس صفحه را نگه می‌دارد.** `history.replaceState` در بوت هش را روی صفحهٔ جاری می‌گذارد، پس یک رفرش به همان صفحه برمی‌گردد نه به تب اول.
- **برگشت روی پنجرهٔ باز، اول پنجره را می‌بندد.** اگر موقع برگشت یک `.overlay` یا `.sheet` باز باشد، همان Escape را می‌گیرد و entry صفحه دوباره push می‌شود تا خواننده از کاری که وسطش بوده جدا نشود.

## ذخیره‌سازی

همهٔ داده‌های کاربر محلی است و در همین مرورگر می‌ماند.

| داده | محل |
|---|---|
| کارها، نام، تم، تاریخ روزهای فعال، مودها، تنظیمات تمرکز، جلسهٔ در جریان، سابقهٔ تمرکز | `localStorage` (کلیدهای `daftarche-*`) |
| متادیتای کتاب‌ها (پیشرفت، صفحه‌های خوانده‌شده، هدف، هایلایت‌ها، یادداشت‌ها) | `localStorage` |
| فایل PDF کتاب‌ها | `IndexedDB` — دیتابیس `daftarche-books`، store `books` |
| موسیقی‌هایی که خودت بارگذاری می‌کنی | `IndexedDB` — دیتابیس `daftarche-audio`، store `tracks` |

«پاک کردن همهٔ داده‌ها» در پروفایل، دادهٔ کاربر را پاک می‌کند: هر دو دیتابیس IndexedDB (کتاب‌ها و موسیقی بارگذاری‌شده) و `localStorage`. کش آفلاین، ثبت Service Worker و مجوز اعلان‌ها دست‌نخورده می‌مانند. اگر پاک‌سازی کامل نشود، برنامه پیام خطای صریح می‌دهد.

فایل‌های PDF هرگز از کش مرورگر رد نمی‌شوند؛ فقط خود اپ در کش آفلاین ذخیره می‌شود.

## PWA

- **نصب‌پذیری:** `manifest.webmanifest` با `display: standalone`، `start_url` و `scope` نسبی، و آیکون‌های `any` و `maskable`. رنگ نوار مرورگر از `theme-color` می‌آید و با تم فعال (روشن/تاریک) هماهنگ می‌شود.
- **پوستهٔ آفلاین:** `sw.js` فهرست `SHELL` را در زمان نصب به‌صورت یک مجموعه کش می‌کند — صفحه، همهٔ CSS و ماژول‌های JS، فونت‌ها، آیکون‌ها و تصویرهای شخصیت‌ها. اپ بدون شبکه هم بالا می‌آید.
- **کش هر انتشار:** نام کش‌ها از نسخهٔ build ساخته می‌شود (`daftarche-static-<BUILD>` و `daftarche-runtime-<BUILD>`). یک انتشار به‌صورت یک کلیت اعمال می‌شود؛ هرگز نیمه‌قدیم و نیمه‌جدید سرو نمی‌شود.
- **pdf.js:** نسخهٔ پین‌شدهٔ pdf.js از CDN با استراتژی cache-first در کش runtime نگه داشته می‌شود تا خواننده آفلاین هم کار کند. فایل‌های کمکی آن (cmaps و فونت‌های استاندارد) در صورت نیاز کش می‌شوند.
- **سازگاری ریشه و زیرمسیر:** همهٔ مسیرها نسبت به مکان خود فایل resolve می‌شوند، پس اپ هم روی `https://domain/` و هم روی زیرمسیری مثل `https://domain/daftarche/` درست کار می‌کند — از جمله مقصد کلیک اعلان‌ها، آیکون و badge آن‌ها.
- **به‌روزرسانی:** هیچ‌وقت اجباری نیست. کارگر جدید بی‌صدا نصب می‌شود و فقط وقتی جایگزین می‌شود که صفحه اجازه بدهد (تپ روی اعلان به‌روزرسانی) یا در پس‌زمینه و وقتی برگه پنهان است.

## نسخه‌گذاری و انتشار

**تنها محل نوشتن شمارهٔ نسخه: `js/version.js`.**

```js
self.DAFTARCHE_RELEASE = '2.0.0';   // نسخهٔ محصول
self.DAFTARCHE_BUILD   = 'v20';     // نسخهٔ build آفلاین
```

(مقدارها نمونه‌اند و با هر انتشار جلو می‌روند؛ مرجع، خودِ `js/version.js` است.)

| مفهوم | یعنی چه | کجا مصرف می‌شود |
|---|---|---|
| `RELEASE` | نسخهٔ محصول که کاربر می‌بیند (مثل `2.0.0`). | شمارهٔ نسخه در تنظیمات پروفایل، دیالوگ «چی تغییر کرد؟»، ورودی `CHANGELOG` در `js/changelog.js`، و سابقهٔ `CHANGELOG.md`. |
| `BUILD` | نام build آفلاین؛ کلید کش‌های Service Worker. | نام هر دو کش، و اینکه کارگر جدید اصلاً نصب شود یا نه. |

قواعد:

1. **هر تغییری در فایل‌های پوسته، `BUILD` را جلو می‌برد.** فایل‌های پوسته همان فهرست `SHELL` در `sw.js` است: `index.html`، `manifest.webmanifest`، همهٔ `css/`، همهٔ `js/` (شامل خود `js/version.js`) و دارایی‌های فونت/آیکون/شخصیت.
2. **`RELEASE` در همان فایل جلو می‌رود** و همراه آن یک ورودی به `CHANGELOG` در `js/changelog.js` (برای دیالوگ درون‌برنامه‌ای) و یک بخش در `CHANGELOG.md` (برای سابقهٔ انتشار) اضافه می‌شود.
3. `sw.js` این فایل را با `importScripts` می‌خواند و خودش شمارهٔ مستقل ندارد. صفحه هم همان را با یک `<script>` کلاسیک پیش از ورودی ماژول می‌خواند. پس نسخهٔ محصول، نسخهٔ کش و نسخهٔ Service Worker **از هم جدا نیستند** و نمی‌توانند از هم فاصله بگیرند.
4. **بالا بردن `RELEASE` همان چیزی است که «چی تغییر کرد؟» را به کاربر می‌رساند.** این دیالوگ دو نسخه را مقایسه می‌کند، پس فقط برای کسی باز می‌شود که نسخهٔ قبلی را روی همین دستگاه اجرا کرده باشد. شمارهٔ تأییدشدهٔ کاربر در `localStorage` می‌ماند (`daftarche-seen-version`) و در اولین اجرا نسخهٔ فعلی بی‌صدا ثبت می‌شود تا انتشار بعدی اعلام شود. **این دیالوگ هیچ دکمهٔ ورودی در رابط ندارد** — نه در پروفایل و نه جای دیگر؛ تنها راه باز شدنش همین بررسی هنگام راه‌اندازی است، پس کاربر تازه‌وارد هرگز آن را نمی‌بیند. اگر `RELEASE` جلو نرود، هیچ‌کس دیالوگ را نمی‌بیند.
5. **انتشار بدون بالا بردن `BUILD` عمداً به کاربران نصب‌شده تحمیل نمی‌شود.** برنامه نصب‌شده همان build منسجم قبلی را نگه می‌دارد تا وقتی `BUILD` عوض شود. اگر فایلی از پوسته را تغییر بدهی و `BUILD` را جلو نبری، آن تغییر به client نصب‌شده نمی‌رسد (به بازدید تازه می‌رسد).

### چرخهٔ به‌روزرسانی

```
deploy → مرورگر sw.js را تازه می‌گیرد (updateViaCache: 'none')
       → BUILD عوض شده ⇒ install: کش کاملِ build جدید ساخته می‌شود
       → activate: کش‌های daftarche-* قدیمی حذف می‌شوند
       → صفحه اعلان به‌روزرسانی را نشان می‌دهد (یا در پس‌زمینه بی‌صدا تحویل می‌شود)
       → بعد از تعویض کارگر، صفحه یک بار reload می‌شود
```

اگر فقط `RELEASE` جلو رفته باشد و هیچ فایل پوسته‌ای عوض نشده باشد، نصب دوباره کل کش را دانلود نمی‌کند و فقط نشانگر نسخه را تازه می‌کند.

اعلان به‌روزرسانی بلافاصله نمی‌آید. تا وقتی کاربر دستش روی کیبورد است، توی جلسهٔ تمرکز است، رویه‌ای باز است، توست بازگردانی گوشهٔ صفحه را گرفته، یا صفحه روی نمایش نیست، پیام نگه داشته می‌شود و در اولین لحظهٔ آزاد می‌آید (و اگر صفحه در پس‌زمینه باشد، تحویل بی‌صدا همان‌طور انجام می‌شود).

### چک‌لیست پیش از انتشار

1. تغییرات محصول کامل شود.
2. QA انجام شود.
3. در `js/version.js`: `RELEASE` (و اگر فایلی از پوسته عوض شده، `BUILD`) به‌روزرسانی شود.
4. ورودی `js/changelog.js` و بخش `CHANGELOG.md` اضافه شود.
5. انتشار انجام شود.
6. به‌روزرسانی Service Worker بررسی شود: اعلان به‌روزرسانی بیاید، پس از تعویض کارگر نسخهٔ جدید سرو شود و کش قدیمی حذف شده باشد.

## صفحهٔ آمار

آمارِ دفترچه یک صفحه است، نه چند بخش پراکنده: کارت «آمار من» در پروفایل تنها دَرِ ورود به آن است، و بینش‌ها هم بخشی از همان صفحه‌اند («چیزهایی که دیدیم»). چهار کارت آماری قدیمیِ پروفایل برداشته شد تا آمار فقط یک جا گفته شود.

- **بازه‌ها چرخشی‌اند، نه تقویمی.** «۳۰ روز» یعنی همین ۳۰ روز گذشته (با احتساب امروز)، نه «این ماه»؛ پس یک بازه هیچ‌وقت فقط به این دلیل خالی نیست که ماه تازه شروع شده، و هر بازه با بازهٔ هم‌طول قبلی‌اش قابل مقایسه است.
- **پنج بازه:** ۷، ۳۰، ۹۰، ۱۸۰ و ۳۶۵ روز — دو تای اول روزبه‌روز، سه‌ماهه هفته‌به‌هفته و دو تای آخر ماه‌به‌ماه. بازه‌ای که خواننده انتخاب می‌کند در `daftarche-stats-range` می‌ماند و دفعهٔ بعد همان باز می‌شود.
- **هیچ عددی ساخته نمی‌شود.** بخشی که داده‌ای پشتش نیست پنهان می‌ماند (نه صفر)، نرخ بدون مخرج `null` است، و بازهٔ خالی یک جملهٔ صادقانه می‌گیرد نه دیوار صفر.
- **حلقهٔ پیشرفت مال همین صفحه است** و نرخ تکمیل همان بازه را نشان می‌دهد؛ فوتر لیست کارها فقط شمارندهٔ خودش را دارد. نمودار هفتگی و نشان زنجیره هم از `week.js` به `stats.js` منتقل شدند، چون هیچ‌وقت فقط «این هفته» نبودند.
- **سابقهٔ تمرکز هم داخل همین صفحه است.** فهرست جلسه‌های تمرکز با همان بازه‌ای می‌آید که انتخاب می‌کنی — عنوان کار، مدت، روز، حالِ جلسه و رسیدن یا نرسیدن به کار — شش جلسهٔ اول دیده می‌شود و بقیه با یک دکمه باز می‌شوند. صفحهٔ جدا و کارت پروفایل برداشته شدند.

### کارت آمار

دکمهٔ «کارت آمار» یک تصویر مربعی ۱۰۸۰×۱۰۸۰ می‌سازد: کاغذ و چسب، صورتِ خواننده (عکس یا همدم)، پنجرهٔ انتخابی با تاریخ کاملش، سه عدد از سرصفحه، بیشترین و کمترین دسته، شکل بازه به‌صورت نمودار میله‌ای و یک جملهٔ پایانی.

- **کارت فقط عدد و نمودار است، نه محتوای کارها.** هیچ عنوان کاری روی آن نمی‌رود؛ تنها چیزهای شخصی، اسم و عکس خودِ خواننده‌اند و آن هم فقط اگر گذاشته باشد.
- **قالب کارت انتخابِ خودت است: یک رنگ و یک شکل.** پالت‌ها در `css/base.css` روی `[data-palette]` به‌صورت `--card-*` نوشته شده‌اند و همان مقادیر نقطهٔ رنگی چیپ‌های انتخاب را هم می‌کشند، پس چیزی که می‌بینی همان چیزی است که چاپ می‌شود. قالب «برنامه» به توکن‌های رابط اشاره می‌کند — کارتِ خوانندهٔ تم تاریک تاریک می‌ماند — و «کاغذ»، «شب» و «جنگل» پالت ثابت خودشان را دارند.
- **مسیر تحویل برابر است:** اگر مرورگر بتواند فایل را به share sheet سیستم بدهد همان می‌شود، وگرنه همان PNG ذخیره می‌شود؛ هر دو دکمه همیشه روی پیش‌نمایش هستند و نگه‌داشتن انگشت روی گوشی راه سومی است. قلم‌ها پیش از کشیدن کارت بار می‌شوند و اگر بار نشوند، کارت با قلم سیستم ساخته می‌شود.
- **دکمه وسط صفحه باز می‌شود، نه روی نوار پایین.** گفت‌وگو یک `overlay` است (مثل کارت نام)، پس پردهٔ مات و بلورش را همان لایهٔ مشترک می‌آورد، فوکوس و قفل اسکرول را همان `js/modal.js` نگه می‌دارد، و پنل هیچ‌وقت روی تب‌بار نمی‌افتد.
- **چیدمان روی یک محور وسط بسته می‌شود:** برند و چیپ بازه دو سر یک نوار، صورت و اسم و عنوان بازه و دو سر تاریخ روی خط وسط، ستون‌های اعداد متقارن با جداکننده‌های آینه‌ای، و هر ردیف دسته خودش آینه‌ای است (نام، میله، شمارش). از آن‌جا به پایین کارت روی یک مکان‌نما پیش می‌رود و نمودار ارتفاع باقی‌مانده را برمی‌دارد، پس کارتی که دسته‌بندی پشتش نیست جای خالی حمل نمی‌کند.
- **اول عکس پروفایل، بعد همدم.** روی کارت همان قاعدهٔ پروفایل است: اگر عکس گذاشته باشی همان می‌آید، وگرنه کاراکتری که انتخاب کرده‌ای. صورت در دایرهٔ وسط می‌نشیند و اسم زیرش، پس هیچ واژه‌ای روی صورت نمی‌افتد؛ اسم هر چقدر هم بلند باشد با سه‌نقطه کوتاه می‌شود.
- **کارت به چهار چیز نگاه می‌کند:** کارهای انجام‌شده، روزهای پیاپی، روزهای فعال، و بیشترین و کمترین دسته («درس بیشتر، پروژه کمتر») — دو ردیف از یک فهرست، نه جدول کامل. تاریخ بازه هم کامل و بدون جداکنندهٔ هزارگان نوشته می‌شود: ۱۴۰۵، نه ۱٬۴۰۵.
- **پنل خود کارت کوچک‌ترین پنل اپ است.** عرضش محدود و وسط‌چین است و ارتفاعش سقف دارد، پس چیزی که دیده می‌شود کارت مربعی است، نه صفحه‌ای که کارت را در خودش گم کرده باشد.

- **سه شکل، هرکدام با سهم متفاوتی از جا.** «کلاسیک» کارت کامل است: لغزش خط‌چین عددها و دو ردیف دسته‌بندی. «فشرده» لغزش را برمی‌دارد، یک ردیف دسته‌بندی نگه می‌دارد و جا را به نمودار می‌دهد. «شاخص» سرصفحه را یک عدد بزرگ می‌کند، بقیه عددها را قرص‌های زیرش می‌آورد و نمودار را بلندتر می‌کند.
- **تپ روی هر چیپ همان لحظه کارت را از نو می‌کشد.** ردیف رنگ و ردیف شکل زیر پیش‌نمایش می‌نشینند و مثل سوییچ بازه در صفحهٔ آمار رفتار می‌کنند: یک رادیو با یک توقف تَب، جابه‌جایی با کلیدهای چپ و راست. تا وقتی کارت تازه آماده نشده، پیش‌نمایش کم‌رنگ می‌شود تا «هنوز نهایی نیست» را بگوید.
- **انتخاب میان نسخه‌ها می‌ماند** (`daftarche-card-style`، کنار دیگر تنظیمات `localStorage`)؛ مقدار ناشناخته یا خراب بی‌صدا به جفت پیش‌فرض («برنامه» + «کلاسیک») برمی‌گردد.

## Web Push — جزء اختیاری سرور

یادآورهای محلی در خود اپ کار می‌کنند و برای آن‌ها هیچ سروری لازم نیست. کنار آن، یک لایهٔ **اختیاری** Web Push وجود دارد:

- سمت کلاینت: `js/notifications.js` یادآور محلی را از تپ روی زنگ کار زمان‌بندی می‌کند. ماژول `js/push-service.js` نگه داشته شده اما در انتشار فعلی خاموش است؛ نه اشتراکی ساخته می‌شود و نه درخواستی به سرور push می‌رود.
- سمت سرور: پوشهٔ `server/` — یک سرویس Express که اشتراک‌ها را نگه می‌دارد و یادآورهای موعد را با VAPID می‌فرستد. مستندات کامل در [`server/README.md`](server/README.md).
- اگر سرور در دسترس نباشد، Web Push بی‌صدا خاموش می‌ماند و یادآورهای محلی تنها کار می‌کنند.

وضعیت فعلی، صریح:

- این لایه در انتشار فعلی **قابلیت محصول نیست**: خاموش است و به آینده موکول شده. تکمیل آن به یک زمان‌بند بیرونی و معماری همگام‌سازی کارها فراتر از local-first فعلی نیاز دارد؛ بدون آن حتی اشتراکی هم ساخته نمی‌شود.
- میزبانی استاتیک (مثل GitHub Pages) **خودش زمان‌بند ندارد**؛ برای یادآورهای موعد، یک زمان‌بند بیرونی (cron) باید endpoint سرور را صدا بزند. بدون آن، هیچ اعلان push ارسال نمی‌شود.
- کلیدهای VAPID و `ADMIN_API_KEY` فقط از محیط سرور تزریق می‌شوند و هرگز در فرانت‌اند، گیت یا لاگ قرار نمی‌گیرند.

## اجرای محلی

اپ ماژول ES و Service Worker دارد، پس با باز کردن مستقیم فایل (`file://`) کار نمی‌کند و به یک سرور استاتیک روی HTTP نیاز دارد:

```bash
python -m http.server 8000
# سپس http://127.0.0.1:8000/
```

برای آزمایش روی زیرمسیر، همان پوشه را داخل یک زیرپوشه بگذار و از `http://127.0.0.1:8000/daftarche/` باز کن.

سرور اختیاری Push:

```bash
cd server
npm install
npm run keys      # ساخت جفت کلید VAPID (یک‌بار)
npm start
```
