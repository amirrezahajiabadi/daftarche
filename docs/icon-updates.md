# به‌روزرسانی آیکون‌ها

آدرس آیکون‌های وب و manifest شامل `asset` است که از SHA-256 محتوای همان فایل می‌آید؛ شمارهٔ نسخه نیست. با تغییر تصویر، آدرس هم عوض می‌شود تا کش favicon و تشخیص تغییر هویت اپ در مرورگر، تصویر تازه را ببیند. هویت نصب (`id`)، `start_url`، `scope` و آدرس manifest ثابت می‌مانند؛ اپ تازه یا نصب دوم ساخته نمی‌شود.

بعد از تغییر هر آیکون:

```sh
node scripts/sync-icons.mjs
node --test
```

اسکریپت فقط ارجاع‌های `index.html` و `manifest.webmanifest` را همگام می‌کند؛ تصویرها را تغییر نمی‌دهد. طبق قواعد پروژه، `BUILD` در `js/version.js` را هم جلو ببرید. برای کنترل بدون نوشتن از `node scripts/sync-icons.mjs --check` استفاده کنید. تست‌ها آدرس‌های کهنه را رد می‌کنند.

Service Worker آیکون‌های نسخه‌دار را از فایل متناظر در کش همان build پاسخ می‌دهد؛ پس بعد از پذیرش آپدیت و بارگذاری مجدد، آیکون وب هم تازه است و آفلاین هم کار می‌کند. این تطبیق فقط برای آیکون‌های فهرست `SHELL` است و پارامتر فایل‌های دیگر را نادیده نمی‌گیرد. هیچ کش یا دادهٔ کاربری پاک نمی‌شود؛ فقط کش پوستهٔ build قبلی طبق روال موجود کنار می‌رود.

## محدودیت دستگاه و مرورگر

آپدیت داخل برنامه، پوسته و ارجاع‌های آیکون را به‌روز می‌کند؛ تغییر آیکون ذخیره‌شده در لانچر/صفحهٔ اصلی را سیستم‌عامل و مرورگر مدیریت می‌کنند، نه JavaScript برنامه. Chrome 144 به بعد برای تشخیص تغییر آیکون به تغییر URL یا metadata در manifest نیاز دارد. تغییر محسوس هویت ممکن است نیازمند تأیید کاربر در گزینهٔ «Review app update» باشد. حذف اپ لازم نیست، ولی تغییر آیکون لانچر الزاماً هم‌زمان با کلیک روی آپدیت نیست.

برای Web Clip یا مرورگری که تغییر آیکون نصب‌شده را پشتیبانی نمی‌کند، اجبار به تعویض آیکون از داخل وب‌اپ ممکن نیست؛ آیکون تازه برای نصب‌های بعدی و نسخهٔ وب فراهم است. به‌خصوص نباید تعویض فوری آیکون صفحهٔ اصلی iOS را وعده داد.

مرجع رسمی Chrome: <https://developer.chrome.com/blog/improvements-to-web-app-updates>
